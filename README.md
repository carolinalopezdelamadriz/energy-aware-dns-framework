# Energy-Aware DNS Framework

**Framework-Based Energy-Aware Analysis of Encrypted DNS: The Carbon Cost of Privacy**

This framework has been created to measure the traffic generated by classic DNS, DNS over HTTPS (DoH), and DNS over QUIC (DoQ), both in isolation and during real web browsing, and convert the measured bytes into an energy and CO2 estimate.

Privacy-preserving DNS has a cost that is normally invisible to whoever deploys it. Making that cost explicit and measurable is what lets protocol and deployment choices (e.g. whether to reuse a connection across queries) be based on data instead of assumption — a small, concrete step toward the kind of resource-efficient, well-informed Internet infrastructure that sustainability goals like the UN's SDG 9, 12, and 13 call for. The framework is released openly so those measurements are reproducible and reusable by others working on the same question.

## Overview

The framework looks at the problem from several angles:

- Isolated DNS resolution, comparing classic DNS, DoH, and DoQ under the same conditions.
- Real web browsing, via Selenium and the Chrome DevTools Protocol (CDP), capturing both the resources the browser sees and the traffic that actually crosses the network.
- Packet/burst patterns, since packet sizes and timing remain observable even when the traffic itself is encrypted.
- Protocol overhead, broken down into handshake, control, and payload bytes.
- Data-quality checks that flag anomalous or contaminated web visits instead of silently averaging them in.
- An energy and CO2 estimate derived from the measured bytes.

A central idea in the framework is the distinction between what Chrome/CDP considers a web resource and what actually travels over the network:

- **CDP** reports web resources: HTML, JavaScript, images, fonts, and so on.
- **PCAP** captures everything that crosses the network interface: DNS, TLS, QUIC, headers, ACKs, handshakes, and other control traffic that CDP never sees.

Comparing the two is what makes it possible to quantify protocol overhead directly, instead of estimating it from theory. Every encrypted experiment (DoH, DoQ, web) also exports its TLS/QUIC session keys in the standard NSS key log format, alongside the capture, so a pcap can be decrypted and inspected in Wireshark afterwards without that changing the traffic being measured.

The carbon model is simple: it treats measured bytes as a proxy for energy, using a fixed, documented energy-per-byte and grid carbon-intensity figure. It produces an **estimate for comparing protocols and websites under the same model**, not a measurement of the energy consumption of the Internet as a whole. See [Carbon model](#carbon-model) below.

## Repository structure

```text
energy-aware-dns-framework/
├── src/            # framework code (see below)
├── data/           # website samples used by the experiments
├── tests/          # unit tests for the framework's pure logic
├── results/        # experiment output (mostly untracked, see .gitignore)
├── docs/           # reproducibility notes, if any beyond this README
├── requirements.txt
├── LICENSE
└── README.md
```

`src/` is a flat package; each file corresponds to one stage of the pipeline:

| File | Role |
| --- | --- |
| `main.py` | CLI entry point; parses arguments and dispatches to the right mode |
| `env_check.py` | Checks that the required tools and Python packages are available |
| `batch_experiment.py` | Runs DNS + web experiments across a list of sites |
| `dns_experiment.py` | Runs one DNS/DoH/DoQ experiment (resolve, capture, analyze, save) |
| `dns_resolver.py`, `doh_resolver.py`, `doq_resolver.py` | Protocol-specific resolution logic |
| `web_experiment.py` | Runs one web visit (browse, capture, analyze, save) |
| `browser.py` | Selenium/Chrome setup, CDP profiling, resource classification |
| `capture.py` | `tcpdump` wrapper: starts and stops a packet capture |
| `analyzer.py` | Per-experiment byte counting from a pcap |
| `overhead_breakdown.py` | Decrypts a pcap with its session keys and splits bytes into handshake/control/payload |
| `burst_analysis.py` | Extracts packet burst features (size, direction, timing) from a pcap |
| `cfp.py` | Converts bytes into an energy and CO2 estimate |
| `results.py` | Small I/O helpers: output directories, CSV rows, JSON files |
| `run_analysis.py` | Loads a saved run and produces the aggregated tables, statistics, and figures |

## Requirements

**General:**

- Python 3.9+
- Google Chrome and a matching ChromeDriver (used by Selenium)
- `tcpdump`
- `tshark` (comes with Wireshark) — decrypts each pcap with its saved session-key log to split bytes into handshake/control/payload
- `kdig` with QUIC support — fallback DoQ client (`knot` package on most systems)
- Python dependencies from `requirements.txt`

**macOS-specific** (the framework was developed and tested on macOS; other platforms have not been verified):

- `kdig` is installed via `brew install knot`.
- The default network interface name (`en0`) and the permission notes below assume macOS. On Linux, the interface name and `tcpdump` permission model are different; the framework has not been tested there.

Install the Python dependencies:

```bash
pip install -r requirements.txt
```

DoQ additionally needs `aioquic`; DoH needs `httpx` with HTTP/2 support (the `h2` package, pulled in via `httpx[http2]` in `requirements.txt`) — Quad9's DoH endpoint requires HTTP/2 and rejects HTTP/1.1 outright. Both are already listed in `requirements.txt`.

## Environment check

Before running experiments, check that the local setup has everything it needs:

```bash
python3 src/main.py --mode check --interface en0
```

To also check DoQ connectivity from the current network:

```bash
python3 src/main.py --mode check --interface en0 --check-doq --doq-resolver quad9
```

`tcpdump` normally needs administrator privileges to capture. If the machine already has BPF device permissions configured (for example, from a previous Wireshark installation), it can capture as a regular user — `--mode check` reports which case applies before defaulting to `sudo` for every run. Running with `sudo` leaves everything under `results/` owned by `root`, which then blocks `--mode analyze` afterwards unless that is also run with `sudo`.

## Quick start

A minimal example before running the full experiment: two DNS protocols, three repetitions, against a single domain.

```bash
python3 src/main.py \
  --mode dns \
  --protocols dns doh \
  --domain example.com \
  --repetitions 3 \
  --interface en0
```

This writes a new timestamped folder under `results/` containing the pcap captures, key logs, and a `dns_results.csv` row per protocol. See [Analyzing a run](#analyzing-a-run) for how to turn that into summaries and figures.

## Running experiments

### DNS experiment

```bash
python3 src/main.py --mode dns --protocols dns doh doq --domain bbc.com --repetitions 5 --interface en0
```

`--connection-mode` controls how the encrypted protocols reuse (or don't reuse) their connection across repetitions: `cold_start` (default; a new connection per query), `amortized` (one connection for the whole batch), or `both`.

### Web experiment

```bash
python3 src/main.py --mode web --url https://www.bbc.com --interface en0
```

`--headless` runs Chrome without a visible window; `--fresh-profile` uses an isolated, temporary Chrome profile per visit, so cache and service workers from a previous visit don't affect the CDP byte count.

### Batch experiment

Runs DNS and web experiments across every site in a CSV file (see [Website sample](#website-sample)):

```bash
python3 src/main.py \
  --mode batch \
  --sites-file data/sites_100.csv \
  --protocols dns doh doq \
  --repetitions 5 \
  --web-repetitions 1 \
  --interface en0 \
  --doq-resolver quad9 \
  --headless \
  --fresh-profile \
  --site-delay 5
```

`--site-delay` pauses between sites to avoid saturating the local network. `--skip-dns` and `--skip-web` restrict a batch run to only one side of the experiment.

Each run writes a new folder under `results/`, named after the timestamp it started:

```text
results/<run_id>/
├── manifest.json                          # run configuration and site list
├── dns_results.csv                        # one row per DNS/DoH/DoQ experiment
├── web_results.csv                        # one row per web visit
├── dns_<protocol>_<timestamp>.pcap
├── dns_<protocol>_<timestamp>.keylog      # empty for classic DNS, nothing to decrypt
├── dns_<protocol>_<timestamp>_bursts.json
├── web_<timestamp>.pcap
├── web_<timestamp>.keylog
├── web_profile_<timestamp>.json
└── web_<timestamp>_bursts.json
```

## Analyzing a run

The experiment and the analysis are separate steps. Once a run has been captured, its figures and summary tables can be regenerated at any time without repeating the network experiment:

```bash
python3 src/main.py --mode analyze --run-dir results/<run_id>
```

This reads the CSVs already written by the experiment and produces `results/<run_id>/analysis/`, including (not an exhaustive list — see the folder after running):

- `summary.md` — a run report: configuration, completion status, and the main tables.
- Per-protocol and per-category summary CSVs (`dns_protocol_summary.csv`, `web_category_summary.csv`, `dns_privacy_cost_by_site.csv`, ...).
- Flagged-visit CSVs (`web_flagged_sites.csv`, `dns_flagged_experiments.csv`) listing which visits were excluded from the aggregates, and why.
- Resource-origin and resource-type breakdowns (`web_origin_summary.csv`, `web_resource_type_summary.csv`).
- Figures (`fig_*.png`): DNS overhead by protocol, handshake/control/payload breakdown, burst patterns, PCAP-vs-CDP comparisons by category, and CO2 by category.

The analysis also applies the data-quality checks described in the thesis: visits that look bot-blocked, whose capture wasn't correctly scoped to the browser's own traffic, or that are statistical outliers relative to the rest of the run are flagged and excluded from the aggregated tables rather than silently averaged in.

## Website sample

The main experiment targets 100 websites (`data/sites_100.csv`), drawn from ten categories with ten sites each: `news`, `banking`, `public_admin`, `education`, `ecommerce`, `technology`, `social_media`, `streaming`, `health`, and `standards`. Two smaller samples are also included for faster iteration: `data/sites_10_pilot.csv` (one site per category) and `data/sites_sample.csv` (a five-site smoke test, used as the default `--sites-file`).

Sites within each category were selected using:

- **Popularity**: ranked in the Tranco top-1M list [4], a research-oriented, manipulation-resistant ranking built from multiple popularity datasets (Alexa, Majestic, Umbrella, Quantcast).
- **Geographic diversity**: both internationally dominant sites and Spanish-language or Spanish-hosted sites, reflecting the European regulatory context (GDPR) and the use of a European resolver (Quad9).
- **Balance**: ten sites per category, to avoid statistical bias toward any single sector.
- **Accessibility**: sites reachable without authentication, so Selenium can capture a complete page load.

The category split follows the taxonomy used by Cloudflare Radar and the traffic-category breakdown reported in The Shift Project's *Lean ICT: Towards Digital Sobriety* report [1], which identifies streaming, social media, and news as dominant categories of Internet traffic by volume.

References: [1] The Shift Project (2019), *Lean ICT: Towards Digital Sobriety*. [2] Böttger et al. (2019), *An empirical study of the cost of DNS-over-HTTPS*, ACM IMC. DOI: 10.1145/3355369.3355575. [3] Hounsel et al. (2020), *Comparing the effects of DNS, DoT, and DoH on web performance*, The Web Conference. DOI: 10.1145/3366423.3380139. [4] Le Pochat et al. (2019), *Tranco: A research-oriented top sites ranking hardened against manipulation*, NDSS. DOI: 10.14722/ndss.2019.23386.

## Carbon model

```text
E[J]        = bytes * energy_per_byte_j
E[kWh]      = E[J] / 3.6e6
CO2[kgCO2e] = E[kWh] * co2_per_kwh
```

Implemented in `src/cfp.py`. `bytes` is the measured total from a pcap; `energy_per_byte_j` and `co2_per_kwh` are configurable constants, not measured quantities — by default, the network-transmission energy intensity from the Sustainable Web Design methodology (v4) and the Spanish electricity grid's carbon intensity (CNMC, 2024 data). Both are applied identically across every protocol and every site, so the resulting comparisons stay internally consistent even though their absolute values depend on the constants chosen. Swapping either constant (a different grid, a different energy-intensity study) does not require touching the rest of the pipeline.

This is a **model-based estimate**, not a direct measurement of energy consumption: nothing in this framework reads a power meter or measures device-level, resolver-side, or data-center energy. It converts a byte count into a comparable figure under one consistent set of assumptions.

## Reproducibility

- The website samples are versioned in `data/`, so the exact input to any run is fixed.
- Dependencies are documented in `requirements.txt` with minimum versions.
- Every run gets its own timestamped ID and a `manifest.json` recording the configuration it was run with.
- Raw and intermediate results (pcaps, key logs, per-visit JSON, per-experiment CSV rows) are written to `results/<run_id>/` and kept locally.
- **Analysis can be rerun from an existing run without repeating the network experiment** — `--mode analyze` only reads already-saved CSVs; it never triggers a new capture. This is the same separation the thesis describes: experiment → captured data → analysis → figures/summaries, each a distinct step.
- A handful of reference runs (CSVs, summaries, and figures) are kept in version control under `results/` so the pipeline can be reviewed without repeating the full campaign. The raw pcaps of the definitive run, `results/20260725_002327_final/` (run ID `20260725_002327`, folder renamed to mark it as the definitive one), are also published for that same reason — see [Security and privacy](#security-and-privacy) for what is and isn't included, and why.

## Limitations

- The carbon model is a simplified estimate: energy is inferred from traffic bytes using a fixed, configurable factor, not measured directly. It does not represent the energy consumption of the Internet, or of any specific device, resolver, or data center.
- Results depend on the network conditions, machine, and resolver used at capture time; absolute byte, energy, and CO2 figures are not universal constants for a given protocol.
- Browser behavior (Chrome version, background services, automation detection by some sites) can vary and is not fully controlled for.
- DoQ requires UDP/853 to be reachable and the chosen resolver to respond; results depend on that connectivity being available.
- The website sample is a defined, versioned selection (see [Website sample](#website-sample)), not a random or exhaustive sample of the web.

## Security and privacy

This framework captures real network traffic and, for encrypted protocols, exports the TLS/QUIC session keys needed to decrypt it. Both are sensitive:

- **PCAP files** contain the raw browsing traffic of whichever machine ran the experiment.
- **Key log files** (`.keylog`) contain the session secrets needed to decrypt that traffic. A key log next to its pcap is enough to read the encrypted capture in full.

By default, neither is published: `*.pcap`, `*.pcapng`, and `*.keylog` are excluded via `.gitignore` everywhere in the repository, not only under `results/`. If you fork or extend this framework, keep that exclusion, and treat any pcap/keylog pair you generate as sensitive data.

**Exception:** the raw pcaps of the definitive run (run ID `20260725_002327`, the one the thesis and the accompanying article are based on) are published under `results/20260725_002327_final/` as supplementary material, to support independent verification of the byte counts reported in both. This is a deliberate, narrow exception, not a change to the default: only that one run's pcaps are included, and its `.keylog` files stay excluded like everywhere else — without them, the published pcaps show packet sizes and timing but not decrypted TLS/QUIC content.
